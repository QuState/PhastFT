Dispatched scalar formulation versus explicit SIMD: four-pass FFT

Historical experiment: the dispatch wrapper, forced inlining and auto mode
were subsequently removed. Commands and validation below describe the measured
experimental version, not the current source.

Date: 2026-10-21
CPU: AMD Ryzen 9 9950X, 16 cores / 16 online logical CPUs
Binary SHA-256: 18ab282fe31d87df3bcff0b32c22ae8d602c87024b6ea0478cabf3d736ea1c60
Build: cargo build --release --offline --example benchmark_four_pass
No RUSTFLAGS or target-cpu override.

Conclusion:
The dispatch context enables AVX-512 auto-vectorization but does not improve
whole-FFT performance here. Auto is 6.2-9.6% slower than scalar on one thread.
At 16 threads, auto is 4.5%/1.0% slower at 64 MiB (f64/f32), and effectively
tied with scalar at 2 GiB (+0.06%/+0.46%, within observed run variation).
Hand-written direct SIMD remains clearly faster than scalar on one thread at
64 MiB (8.9%/8.8% less time) and at 2 GiB for f64 (5.0% less time). Its 0.47%
advantage for f32 at 2 GiB is small. Keep the hand-written implementation and
the scalar default. The auto experiment was subsequently removed.

Change:
- Force-inline the original generic transpose_columns loop, without modifying
  its packing, initialization, indexing or loop structure.
- FOUR_PASS_TRANSPOSE=auto calls that loop inside fearless_simd::dispatch!,
  using the detected SIMD level. This enables LLVM's target-specific optimizations
  without introducing explicit vector types or operations in the loop.
- The same force-inlined loop is also used by the scalar baseline outside dispatch.
- All four variants are remeasured in this rebuilt executable; results are not
  pooled with the previous executable. Default remains scalar.
- Disassembly of the actual benchmark executable confirms AVX-512 gathers and
  512-bit stores, not a register transpose. See four_pass_auto_disassembly.txt.

Input sizes and layout:
64 MiB = 67,108,864 bytes: f64 2^22, matrix 512 x 8192;
                         f32 2^23, matrix 512 x 16384.
2 GiB = 2,147,483,648 bytes: f64 2^27, matrix 2048 x 65536;
                           f32 2^28, matrix 4096 x 65536.
Bytes count real plus imaginary arrays. Scratch adds the same size again,
plus small plans and local temporary storage. Matrix split and tiling unchanged.

Method:
- RAYON_NUM_THREADS=1, taskset -c 2; then RAYON_NUM_THREADS=16, taskset -c 0-15.
- Same parallel build for both thread counts. Local FFT parallelism disabled
  by the existing prototype; one-worker runs are confined to one CPU core.
- Four rotating blocks: scalar/auto/simd/direct, auto/simd/direct/scalar,
  simd/direct/scalar/auto, direct/scalar/auto/simd.
- Each process has one excluded warm-up, followed by measured transforms.
- 64 MiB: 4 x 20 = 80 samples per precision/variant/thread count.
- 2 GiB: 4 x 4 = 16 samples per precision/variant at one thread;
         4 x 5 = 20 samples at 16 threads.
- For each thread count: 64 MiB f64, 64 MiB f32, 2 GiB f64, 2 GiB f32.
- Input regenerated from the same seed outside each timed region. Planning,
  allocation, input generation and initial scratch page touching excluded.
- FOUR_PASS_PROFILE unset. All runs sequential, no concurrent tests or builds.
- Every SIMD variant reports Avx512. All use the same executable.
- Separate both-mode auto checks compare 4096 output bins against DIT for
  every size/precision/thread count; those timings are excluded here.

Validation:
- Release example tests: 8 passed with default features; 8 passed without
  default features. Full FFTs (forward/inverse, powers 0 through 22) use auto
  and hand-written packed SIMD and compare against RustFFT. Exact bit permutation tests include partial
  tiles, offsets, NaNs and signed zero on baseline and detected SIMD levels.
- Existing hand-written SIMD bit-permutation tests also pass.
- cargo clippy --offline --release --example benchmark_four_pass -- -D warnings passed.

Reproduce a timing block (MODE = scalar, auto, simd, direct):
FOUR_PASS_TRANSPOSE=MODE RAYON_NUM_THREADS=1 taskset -c 2 target/release/examples/benchmark_four_pass 64 22 20 four-pass
FOUR_PASS_TRANSPOSE=MODE RAYON_NUM_THREADS=1 taskset -c 2 target/release/examples/benchmark_four_pass 64 27 4 four-pass
For f32 use 32 23 or 32 28. For 16 threads use RAYON_NUM_THREADS=16,
taskset -c 0-15, and 5 measured iterations at 2 GiB.
