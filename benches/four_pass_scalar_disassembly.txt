Scalar transpose disassembly in the measured four-pass benchmark

Binary: target/release/examples/benchmark_four_pass
SHA-256: 5b27454c9c9950db6e98bab8cd639663b8e39ea08050687b1354fd9bf926dcb5
Command: objdump -d -C -Mintel target/release/examples/benchmark_four_pass

The full transpose uses WIDTH=128 and a 32-row stack tile. The generic Rust
loop is inlined into FourPass32/64::transpose_columns<128>. Its scalar branch
contains no AVX instructions, but LLVM does use SSE/SSE2 vector instructions.
The scalar branch starts at 0x69f7f (f32) / 0x6ca41 (f64), selected when the
optional SIMD level is absent. The same wrappers also contain calls to the
explicit SIMD implementation, which are bypassed in scalar mode.

Packing source rows uses memcpy calls (GOT 0x139838, verified with objdump -R).
The instructions executed inside libc memcpy are not determined by these
static excerpts and may themselves use wider vectors through libc dispatch.

Transposing the packed tile:
- f32: eight separate movss loads, four unpcklps and two movlhps instructions
  assemble two XMM vectors; two movups stores write eight f32 values.
- f64: two movsd plus two movhps memory loads assemble two XMM vectors;
  two movups stores write four f64 values. movhps here just copies 64 bits;
  it does not convert the doubles to floats.
- Scalar remainder paths use movss/movsd load-store pairs.
- Address arithmetic, bounds checks and loop control use integer instructions.
- Tile initialization uses shufps/movlhps broadcasts followed by fully unrolled
  movaps stores (1024 stores for f32's 16 KiB tile, 2048 for f64's 32 KiB tile).
  These are static counts, not a measurement of their performance cost.

Thus 'scalar' describes the source implementation, not a ban on compiler SIMD.
The vectorized inner loop still loads one element at a time from different
rows, then combines them into contiguous 128-bit output stores. This differs
from the explicit 512-bit register-transpose network.
