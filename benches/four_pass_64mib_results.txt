Four-pass FFT transpose comparison at 64 MiB

Date: 2026-10-21
CPU: AMD Ryzen 9 9950X, 16 cores / 16 online logical CPUs
Threads: RAYON_NUM_THREADS=16, affinity not pinned
Compiler/build: same release executable as the preceding 2 GiB SIMD experiment;
no code changes, no RUSTFLAGS or target-cpu override.
Binary SHA-256: 5b27454c9c9950db6e98bab8cd639663b8e39ea08050687b1354fd9bf926dcb5

Input size: 67,108,864 bytes (64 MiB) across real and imaginary arrays.
f64: 2^22 = 4,194,304 complex points; matrix 512 x 8192.
f32: 2^23 = 8,388,608 complex points; matrix 512 x 16384.
Scratch adds another 64 MiB. This is not a 64 MiB total working set.

Conclusion:
No whole-FFT speedup from the SIMD transpose at this size with the current
layout. Packed SIMD is about 1% slower for f64 (small compared with timing
spread) and 4.5% slower for f32. Direct SIMD loads are slower in both.
The existing scalar packed transpose remains the default.

Method:
- Unchanged matrix-splitting heuristic, 16-column gather batches,
  128-column transpose bands and 32-row tiles.
- Compare scalar packed, SIMD packed and SIMD direct variants in the same
  executable, selected with FOUR_PASS_TRANSPOSE=scalar|simd|direct.
- Three blocks of 40 measured transforms each: 120 samples per variant,
  per precision. One excluded warm-up in each process.
- Rotate process order by block: scalar/simd/direct, simd/direct/scalar,
  direct/scalar/simd. Run f64 first, then f32, all sequentially.
- Same seeded input regenerated outside timing before each transform.
- Planning, allocation, initial page touching and input generation excluded.
- FOUR_PASS_PROFILE unset for final timing runs; no concurrent tests/builds.
- Separate both-mode runs compare 4096 output bins with DIT for every variant.
- Separate 10-sample profiled runs below are diagnostic, not pooled with timings.
- Runtime logs confirm Avx512 for both SIMD variants, using the same binary
  documented in four_pass_simd_disassembly.txt.

Reproduce one block (substitute scalar, simd or direct for MODE):
FOUR_PASS_TRANSPOSE=MODE RAYON_NUM_THREADS=16 target/release/examples/benchmark_four_pass 64 22 40 four-pass
FOUR_PASS_TRANSPOSE=MODE RAYON_NUM_THREADS=16 target/release/examples/benchmark_four_pass 32 23 40 four-pass

These are measurements of the existing layout, not a retuning for 64 MiB.
In particular, pass 2 has 512/128 = 4 destination bands, so its current
parallel decomposition can use at most four workers at this size. The
other passes can expose more parallel work. The FFT's input plus scratch
is 128 MiB, larger than the CPU's 64 MiB aggregate L3.
